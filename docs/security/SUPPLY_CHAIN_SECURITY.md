## 1. Overview

QODIQA implements a multi-layer supply chain security program covering the full lifecycle from dependency installation through production deployment. added automated verification, SBOM generation, secret scanning, and a security-gated CI pipeline.

**Threat model:** Supply chain attacks can introduce malicious code via:
- Compromised npm packages (direct or transitive)
- Malicious lifecycle scripts executing during `npm install`
- Secrets committed to version control
- Drift between locked and installed dependency versions
- Undisclosed license or vulnerability exposure in dependencies

## 2. Dependency Pinning Strategy

### 2.1 `package-lock.json` Integrity

All dependencies are pinned via `package-lock.json` at `lockfileVersion: 3`. Every resolved package entry includes a SHA-512 SRI integrity hash generated by the npm registry at publish time:

```
"node_modules/helmet": {
  "version": "8.0.0",
  "integrity": "sha512-<base64>",
  ...
}
```

**npm behavior:** `npm ci` verifies each package's downloaded tarball against the recorded SHA-512 hash before extraction. A tampered package that does not match the recorded hash causes `npm ci` to abort.

### 2.2 Lock File Version Requirements

`verify-supply-chain.js` Check 1 explicitly requires `lockfileVersion >= 2`. Version 1 lock files do not include package-level integrity hashes and are rejected.

### 2.3 Clean Install Policy

All install operations use `npm ci` (not `npm install`):
- **CI pipeline:** `npm ci --omit=dev --ignore-scripts`
- **Dockerfile (deps stage):** `npm ci --omit=dev --ignore-scripts`
- **Test installs:** `npm ci --ignore-scripts`

`npm ci` enforces that `package-lock.json` is present, hash-verified, and matches `package.json`. It never modifies the lock file.

## 3. Supply Chain Verification (`scripts/verify-supply-chain.js`)

 — Run in CI on every pull request and push to `main`/`release` branches.

### Purpose

Performs 6 structural integrity checks beyond what `npm ci` provides. Detects supply chain risks that integrity hash verification alone does not catch.

### Checks

| Check | Description | Failure Action |
|-------|-------------|----------------|
| 1. Lock file version | `lockfileVersion >= 2` required | `process.exit(1)` |
| 2. Integrity hash coverage | Every package (except root) must have a non-empty `integrity` field | FAIL (configurable) |
| 3. Bundle dependencies | Packages with `bundleDependencies` are flagged (can shadow verified packages) | WARN |
| 4. Lifecycle scripts | `preinstall`, `install`, `postinstall` scripts flagged unless in `ALLOWED_SCRIPTED_PACKAGES` | WARN |
| 5. npm audit | `npm audit --audit-level=high` — fails on HIGH or CRITICAL CVEs | FAIL |
| 6. Critical package version deduplication | `helmet`, `cors`, `express`, `jsonwebtoken`, `bcrypt`, `argon2`, `zod` checked for multiple installations | WARN |

### Configuration

| Environment Variable | Default | Purpose |
|---------------------|---------|---------|
| `SUPPLY_CHAIN_FAIL_ON_WARN` | `false` | Treat warnings as failures in strict mode |
| `NPM_AUDIT_LEVEL` | `high` | Minimum CVE severity to fail on |

### Allowed Scripted Packages

The `ALLOWED_SCRIPTED_PACKAGES` set in `verify-supply-chain.js` is intentionally empty. Any package requiring a lifecycle script must be explicitly added after review of the script content and approval from a security reviewer.

### Exit Codes

- `0` — All checks passed (warnings may be present)
- `1` — One or more checks failed

## 4. SBOM Generation (`scripts/generate-sbom.js`)

 — Run in CI on every push to `main`/`release` branches; output archived for 90 days.

### Format

CycloneDX JSON, schema version 1.5. Compliant with NTIA minimum elements for SBOM.

### Component Fields

Each component entry includes:

| Field | Source | Example |
|-------|--------|---------|
| `type` | Always `library` | `"library"` |
| `bom-ref` | PURL | `"pkg:npm/helmet@8.0.0"` |
| `name` | npm package name | `"helmet"` |
| `version` | Locked version from `package-lock.json` | `"8.0.0"` |
| `purl` | Package URL (purl-spec) | `"pkg:npm/helmet@8.0.0"` |
| `scope` | `required` (prod dep) or `optional` (dev dep) | `"required"` |
| `hashes` | SHA-512 (or SHA-1) from `package-lock.json` integrity field, hex-encoded | `[{"alg":"SHA-512","content":"<hex>"}]` |
| `licenses` | SPDX license ID read from installed `package.json` | `[{"license":{"id":"MIT"}}]` |
| `externalReferences` | npm registry tarball URL | `[{"type":"distribution","url":"https://registry.npmjs.org/..."}]` |

### Metadata

The SBOM document includes:

```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "serialNumber": "urn:uuid:<random-uuid4>",
  "version": 1,
  "metadata": {
    "timestamp": "<ISO8601>",
    "tools": [{"vendor": "QODIQA", "name": "generate-sbom", "version": "<pkg.version>"}],
    "component": {"type": "application", "name": "qodiqa", "version": "<pkg.version>"},
    "properties": [
      {"name": "qodiqa:generatedBy", "value": "node v22.x.x on linux"},
      {"name": "qodiqa:prodOnly", "value": "true"},
      {"name": "qodiqa:lockfileVersion", "value": "3"}
    ]
  }
}
```

### Usage

```bash
# Production-only SBOM (default CI mode):
node scripts/generate-sbom.js --prod-only --output sbom.cdx.json

# Full SBOM including devDependencies:
node scripts/generate-sbom.js --output sbom.cdx.json

# Validate output:
npx @cyclonedx/cyclonedx-cli validate --input-file sbom.cdx.json
```

### Deduplication

The generator deduplicates on `name@version` to avoid double-counting packages installed at multiple locations in the `node_modules` tree (hoisted vs. nested).

## 5. Dependency Integrity Verification (`scripts/verify-deps.js`)

 — Run in CI after `npm ci`; optional pre-startup verification.

### Purpose

Verifies that the installed `node_modules` matches `package-lock.json`. Detects:
- Drift (version mismatch between locked and installed)
- Missing packages (declared but not installed)
- Unexpected packages (installed but not in lock file)
- Stale installs (lock file newer than `node_modules`)

### Checks

| Check | Description |
|-------|-------------|
| 1. Version consistency | For each declared dependency: installed `package.json` version must match locked version |
| 2. Unexpected packages | No top-level `node_modules` entry absent from `package-lock.json` |
| 3. Staleness | `node_modules` mtime must be >= `package-lock.json` mtime |

### Options

```bash
# Verify production dependencies only (default):
node scripts/verify-deps.js

# Verify all dependencies including devDependencies:
node scripts/verify-deps.js --strict
```

### Exit Codes

- `0` — All checks passed
- `1` — One or more checks failed

## 6. `npm --ignore-scripts` Policy

**All** npm install operations use `--ignore-scripts`. This policy prevents lifecycle scripts (`preinstall`, `install`, `postinstall`, `prepare`) from executing during package installation.

**Rationale:** Lifecycle scripts are the primary vector for supply chain attacks via npm (e.g., event-stream attack, ua-parser-js attack). By disabling all lifecycle scripts, QODIQA ensures that installing a dependency cannot execute arbitrary code on the build host or in the container.

**Scope of enforcement:**

| Context | Command | Flag |
|---------|---------|------|
| Dockerfile (deps stage) | `npm ci --omit=dev --ignore-scripts` | `--ignore-scripts` |
| CI: dependency-audit job | `npm ci --omit=dev --ignore-scripts` | `--ignore-scripts` |
| CI: sbom job | `npm ci --omit=dev --ignore-scripts` | `--ignore-scripts` |
| CI: dep-verify job | `npm ci --omit=dev --ignore-scripts` | `--ignore-scripts` |
| CI: security-redteam job (`test.yml`) | `npm ci --ignore-scripts` | `--ignore-scripts` |

**Exception process:** Any package that requires a lifecycle script (typically native addons using `node-gyp`) must be added to `ALLOWED_SCRIPTED_PACKAGES` in `scripts/verify-supply-chain.js` after:
1. Manual review of the script content by a security reviewer
2. Documented justification in the PR
3. Supply chain check passing with the explicit allowlist entry

## 7. Secret Scanning (`.gitleaks.toml` + gitleaks)

 — Run on every pull request and push via `gitleaks/gitleaks-action@v2`.

### Configuration

`.gitleaks.toml` extends the gitleaks built-in ruleset with QODIQA-specific rules.

#### QODIQA-Specific Rules

| Rule ID | Pattern | Description |
|---------|---------|-------------|
| `qodiqa-kek` | `(?i)QODIQA_KEY_ENCRYPTION_KEY\s*=\s*[0-9a-f]{64}` | Key Encryption Key — 64 hex chars |
| `qodiqa-sign-token` | `(?i)QODIQA_SIGN_TOKEN\s*=\s*[^\s]{32,}` | Signing token — 32+ chars |
| `qodiqa-ops-token` | `(?i)ok_[0-9a-f]{64}` | Ops bearer token — `ok_` prefix + 64 hex |
| `ed25519-private-key-pem` | `-----BEGIN (PRIVATE\|EC\|RSA) KEY-----` | PEM private key header |
| `redis-password-env` | `(?i)REDIS_PASSWORD\s*=\s*[^\s]{8,}` | Redis password in env var |
| `pg-password-env` | `(?i)(QODIQA_PG_PASSWORD\s*=\s*\|postgresql?://[^:]+:[^@]+@)` | PostgreSQL password |
| `openai-key` | `sk-[A-Za-z0-9]{20,}` | OpenAI API key |

#### Built-in Rules (via `useDefault = true`)

The built-in ruleset covers: AWS access keys, Azure service principal credentials, GCP service account keys, GitHub tokens (`ghp_`, `ghs_`, `gho_`, `github_pat_`), generic high-entropy strings, Slack webhooks, Stripe keys, Twilio auth tokens, and 100+ additional patterns.

#### Allowlist

The `[allowlist]` section suppresses false positives in:

| Category | Pattern |
|----------|---------|
| Example files | `production\.env\.example$` |
| Test directories | `(^|/)test`, `(^|/)tests`, `__tests__`, `\.test\.js$` |
| Test harnesses | `harness\.js$`, `example\.js$` |
| Documentation | `QUICKSTART\.md$`, `README\.md$`, `docs/` |
| Placeholder values | `REPLACE_WITH`, `your-.*-here`, `<YOUR_` |
| All-zero/all-F test keys | `0{64}`, `f{64}` |
| npm integrity hashes | `sha512-[A-Za-z0-9+/=]{86,88}` |
| Git commit SHAs | `[0-9a-f]{40}` |

### Scan Scope

The gitleaks action uses `fetch-depth: 0` (full git history) to detect secrets committed in any historical commit, not just the current HEAD.

### Pre-Commit Usage

```bash
# Scan staged changes before commit (requires gitleaks installed locally):
gitleaks protect --staged --config=.gitleaks.toml

# Scan entire working tree:
gitleaks detect --config=.gitleaks.toml
```

## 8. GitHub Actions Security CI Pipeline (`.github/workflows/security.yml`)

 — Runs on every pull request to `main`/`master`/`release/**` branches and on every push.

> **Test-based security validation lives in `test.yml`, not here.** `security.yml` previously also ran a `security-tests` job (`npm test -- --testPathPattern='phase46'`) under a name ("Security Test Suite") that implied it covered the project's full security/adversarial/red-team test suite. It did not — it ran only the ~6-file `phase46` hardening pattern, while the actual security/adversarial/replay-regression suite never ran in CI at all. That job has been removed from this workflow. The equivalent — and accurately named — coverage now lives in `.github/workflows/test.yml`'s `security-redteam` job ("Security & Red Team Suite"), which runs **both** the `phase46` hardening pattern **and** the real `security`/`adversarial`/`replayRegression` suites (`npx jest --testPathPattern="(security|adversarial|replayRegression|phase46)"`, equivalent to `npm run test:security` plus the hardening subset). See the coverage matrix below.

### Triggers

```yaml
on:
  push:
    branches: [main, master, release/**, hotfix/**]
  pull_request:
    branches: [main, master, release/**]
  schedule:
    - cron: '0 6 * * *'   # Daily at 06:00 UTC
```

The scheduled run catches newly published CVEs in existing dependencies.

### Pipeline Permissions

```yaml
permissions:
  contents: read
  security-events: write  # SARIF upload to GitHub Security tab
```

Minimal permissions: read-only source access and write access only to the Security Events API.

### Jobs

#### Job 1: `dependency-audit`

| Step | Command | Purpose |
|------|---------|---------|
| Checkout | `actions/checkout@v4` (depth 1) | Latest commit only |
| Setup Node.js | `actions/setup-node@v4` (v22, npm cache) | Pin Node.js version |
| Clean install | `npm ci --omit=dev --ignore-scripts` | Verify lock file integrity |
| npm audit | `npm audit --audit-level=high` | Fail on HIGH or CRITICAL CVEs |
| Supply chain check | `node scripts/verify-supply-chain.js` | 6-check structural verification |

#### Job 2: `secret-scan`

| Step | Command | Purpose |
|------|---------|---------|
| Checkout | `actions/checkout@v4` (fetch-depth: 0) | Full history for secret scanning |
| gitleaks | `gitleaks/gitleaks-action@v2` | Scan history for secrets |

Uses `GITHUB_TOKEN` (automatic) and `GITLEAKS_LICENSE` (for gitleaks Enterprise features if licensed).

#### Job 3: `sbom`

| Step | Command | Purpose |
|------|---------|---------|
| Checkout | `actions/checkout@v4` (depth 1) | |
| Clean install | `npm ci --omit=dev --ignore-scripts` | |
| Generate SBOM | `node scripts/generate-sbom.js --prod-only --output sbom.cdx.json` | CycloneDX 1.5 JSON |
| Upload artifact | `actions/upload-artifact@v4` (90-day retention) | Archived as `sbom-<git-sha>` |
| GitHub Dependency Graph | `advanced-security/spdx-dependency-submission-action@v0.1.1` | Optional SBOM upload to GitHub |

#### Job 4: `dep-verify`

| Step | Command | Purpose |
|------|---------|---------|
| Checkout | `actions/checkout@v4` | |
| Clean install | `npm ci --omit=dev --ignore-scripts` | |
| Verify integrity | `node scripts/verify-deps.js` | Version consistency and unexpected package detection |

### Related: Test-Based Security Validation (`.github/workflows/test.yml`)

The `security-redteam` job ("Security & Red Team Suite") is the authoritative CI job for test-based security coverage of this repository. It is defined in `test.yml`, not `security.yml`, but is required alongside the four jobs above for merge.

| Step | Command | Purpose |
|------|---------|---------|
| Checkout | `actions/checkout@v4` | |
| Full install | `npm ci --ignore-scripts` | Including devDependencies for test runner |
| Migrate database | `node src/infra/postgres/migrate.js` | Live Postgres required by some suites |
| Run security, adversarial, replay-regression & hardening tests | `npx jest --testPathPattern="(security\|adversarial\|replayRegression\|phase46)"` | Real security coverage, not just hardening smoke tests |

Injected test secrets via GitHub Actions secrets (`TEST_KEY_ENCRYPTION_KEY`, `TEST_SIGN_TOKEN`). Real secrets are never committed.

**Coverage terminology** — do not use these interchangeably; they cover different, non-overlapping or partially-overlapping things:

| Category | What it covers | Where it runs |
|----------|-----------------|----------------|
| Hardening regression / smoke tests | The narrow `phase46` pattern (~6 files): HTTP-header/CSP/TLS/process/filesystem hardening | `test.yml` → `security-redteam` (subset of its pattern) |
| Security / adversarial / red-team suite | Broader attack-scenario and adversarial-input tests (`security`, `adversarial` patterns) | `test.yml` → `security-redteam` |
| Replay protection validation | `replayRegression` pattern | `test.yml` → `security-redteam` |
| Cryptographic validation | `cryptoRegression`, `hashing`, `ed25519` patterns | `test.yml` → `crypto-regression` (separate job, `npm run test:crypto`) |
| Fail-closed validation | `failclosed.test.js` and related enforcement-path tests | `unit`/`integration` jobs in `test.yml` (path-pattern coverage, no dedicated job) |
| Supply chain / dependency / secret scanning | Everything in Jobs 1–4 above | `security.yml` |
| Full security validation pipeline | The union of all rows above, plus fuzz/chaos/concurrency/mutation suites | Spread across every job in `test.yml` and `security.yml` — no single job is "the" full pipeline |

### Branch Protection Requirements

All 4 jobs in this workflow, plus `test.yml`'s jobs (including `security-redteam`), must pass before a pull request can be merged. Configure via GitHub branch protection rules:
- Required status checks from `security.yml`: `dependency-audit`, `secret-scan`, `sbom`, `dep-verify`
- Required status checks from `test.yml` include `security-redteam` (test-based security coverage) among others — see `test.yml` for the full job list
- Require branches to be up to date before merging

## 9. Container Image Supply Chain

### Build-Time Controls

| Control | Mechanism |
|---------|-----------|
| Base image pinning | `FROM node:22-alpine3.21` — major and minor version pinned |
| No build tools in final image | Multi-stage build; `deps` stage installs, `final` stage only copies output |
| Lifecycle scripts disabled during image build | `npm ci --omit=dev --ignore-scripts` in Dockerfile `deps` stage |
| OCI annotations for traceability | `BUILD_DATE`, `VCS_REF`, `VERSION` labels on final image |
| Sensitive files removed from final image | `RUN rm -rf .env *.pem *.key private.pem data/ audit.log scripts/ docs/ .github/` |

### Image Verification

Generated SBOMs (`sbom-<git-sha>`) in GitHub Actions artifacts can be used to audit the dependency inventory of any specific build. To verify a deployed image:

1. Retrieve the `sbom-<git-sha>` artifact for the build commit
2. Compare SBOM component list against `npm list --prod --json`
3. Verify no unexpected components appear

## 10. Operational Security Checklist for Supply Chain

| Check | Frequency | Responsible |
|-------|-----------|-------------|
| Review all `verify-supply-chain.js` WARN outputs in CI | Per PR | Developer |
| Review new lifecycle-scripted packages flagged by Check 4 | Per PR | Security reviewer |
| Review SBOM diff for newly added dependencies | Per PR | Developer |
| Run `npm audit` manually before production deployments | Pre-deploy | Operator |
| Review gitleaks scan report for false positives needing allowlist | Monthly | Security reviewer |
| Update `ALLOWED_SCRIPTED_PACKAGES` — additions require documented justification | As needed | Security reviewer |
| Pin new dependencies at exact versions (no `^` or `~` ranges for security-critical packages) | Per change | Developer |
| Verify `package-lock.json` is committed and up to date | Per PR | CI (enforced) |
