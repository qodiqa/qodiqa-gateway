# QODIQA Threat Model —

**Version:** 1.0

**Last Updated:** 2026-07-02

---

## 1. System Description

QODIQA is a deterministic AI enforcement gateway built on Node.js 22 and Express 4. Its primary function is to cryptographically enforce consent, policy, and execution binding for AI API calls. Every AI request must carry a signed artifact that proves the request was authorized, has not been replayed, and conforms to the active policy set.

**Core pipeline (5 steps, all fail-closed):**

1. `validateArtifact` — Verify Ed25519 signature over the full envelope (payload + timestamp + expiry + publicKeyId)
2. `verifyRequestBinding` — Confirm the artifact was signed for this exact HTTP request (method, path, body hash)
3. `registerNonce` — Atomically record the requestId in Redis to prevent replay
4. `checkAnomaly` — Evaluate per-key and global rate sliding windows in Redis
5. `enforcePolicy` — Evaluate the live policy set against the request context

**Deployment model:** Single monolith process. Production runs exactly **one** instance (single-node topology with PostgreSQL, `replicas: 1`): a declared `QODIQA_REPLICA_COUNT` above 1 with PostgreSQL enabled is refused at boot (`assertNoIllegalTopology()`, `src/core/audit/multiInstanceGuard.js`) and distributed mode is refused at production boot until (`src/infra/config/bootValidator.js:304-308`). Redis holds nonce/anomaly state; PostgreSQL is mandatory in production.

## 2. Assets Inventory

| Asset | Description | Sensitivity | Location |
|-------|-------------|-------------|----------|
| Ed25519 private signing key | Signs artifact envelopes. Compromise allows forging valid artifacts for any request | Critical | Encrypted at rest (AES-256-GCM with KEK); never in memory longer than required |
| Key Encryption Key (KEK) | AES-256-GCM key that wraps Ed25519 private keys at rest | Critical | `QODIQA_KEY_ENCRYPTION_KEY` env var (64 hex chars); or external KMS (AWS KMS, Azure KV, GCP KMS, HashiCorp Vault, PKCS#11 HSM) |
| Execution invariant secret | HMAC-SHA256 key binding the execution invariant context (`verifiedCtx`) minted after enforcement passes; checked before provider dispatch | Critical | `QODIQA_EXECUTION_INVARIANT_SECRET` env var (64 hex chars); must differ from the KEK (purpose isolation) |
| Ed25519 public keys | Used to verify artifact signatures; stored in key store JSON | Low–Medium | `/opt/qodiqa/data/` (production); path from `QODIQA_KEYS_PATH` env var |
| Ops bearer tokens | Authenticate operator API calls to admin/ops endpoints; `ok_` prefix + 64 hex chars | High | `QODIQA_OPS_TOKEN` env var (shared, deprecated) or per-operator RBAC API key; stored as SHA-256 hash in RBAC store |
| Signing identity API keys | Authenticate `POST /sign` callers; `sk_` prefix + 64 hex chars, individually issued and revocable per identity — no shared secret | High | Issued via `scripts/provision-signing-identity.js` or `POST /signing-identities/:id/api-key`; stored as SHA-256 hash in `src/core/signing/signingIdentityStore.js` |
| Audit log | Hash-chained append-only log of all enforcement decisions; used for compliance and forensics | High | `/opt/qodiqa/logs/` (production); `QODIQA_AUDIT_LOG` env var |
| PostgreSQL audit data | Long-term audit records, RBAC users, tenant configuration | High | Dedicated PostgreSQL instance; `QODIQA_PG_*` env vars |
| Policy files | JSON policy set governing what AI executions are permitted | High | `POLICY_FILE` env var; required (no safe default) in production, see §7.3 |
| Redis nonce store | Set of seen requestIds (UUID v4); expiry-bounded by artifact expiry | Medium | Redis instance; namespace `[<tenantId>:]qodiqa:req:v2:*` |
| Redis anomaly counters | Sliding-window event counts per key and globally | Medium | Redis instance; namespace `anomaly:v2:key:*` and `anomaly:v2:global` |
| API tokens / secrets | AI provider credentials (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `MISTRAL_API_KEY`, `LLAMA_API_KEY`, `LOCAL_API_KEY`), `REDIS_PASSWORD`, `QODIQA_PG_PASSWORD` | High | Environment variables; never logged; redacted in all structured log output. | RBAC user store | User–role mapping, hashed API keys, lifecycle timestamps | High | `QODIQA_RBAC_STORE_PATH` env var; default `data/rbac-users.json` |
| SBOM | Software Bill of Materials (CycloneDX 1.5 JSON) | Low | Generated by `scripts/generate-sbom.js`; uploaded as CI artifact |

## 3. Trust Boundaries

```
Internet
  │
  ▼
[Load Balancer / Reverse Proxy]   ← TLS termination; X-Forwarded-For injection
  │                                  TRUSTED_PROXY must match this IP/CIDR
  │ HTTP (internal)
  ▼
[QODIQA Application Process]      ← hardening applied here
  │        │
  │        ├── [Redis]            ← Nonce store, anomaly store, rate limit store
  │        │    Trusted: yes (same private network); TLS optional via REDIS_TLS
  │        │
  │        └── [PostgreSQL]       ← Audit, RBAC, tenancy
  │             Trusted: yes; TLS required in production (QODIQA_PG_SSL=true)
  │
  └── [AI Provider (openai/anthropic/gemini/mistral/llama/local)] ← External or operator-hosted; see Boundary 5
```

**Boundary 1 — Internet → Load Balancer:**
TLS-terminated by operator infrastructure. QODIQA has no visibility below this layer. Assumed: load balancer strips all client-supplied `X-Forwarded-*` headers before adding its own.

**Boundary 2 — Load Balancer → Application:**
HTTP (plaintext, internal network). `X-Forwarded-For`, `X-Forwarded-Proto`, and `Host` headers are injected by the proxy. QODIQA validates these headers via `src/infra/network/proxyValidation.js`.

**Boundary 3 — Application → Redis:**
QODIQA treats Redis as a shared mutable store with no inherent access control. Redis is trusted but not authoritative — every nonce store result is checked for logical correctness, and Redis failures fail closed (block execution).

**Boundary 4 — Application → PostgreSQL:**
Trusted with full read/write for audit and RBAC records. TLS with `rejectUnauthorized: true` in production. Credentials provided via `QODIQA_PG_PASSWORD` env var or `QODIQA_PG_URL` connection string.

**Boundary 5 — Application → AI Provider:**
QODIQA forwards enforcement-approved requests to one of eight providers (`openai`, `anthropic`, `gemini`, `mistral`, `llama`, `local`, and the experimental `azure`, `bedrock`), selected by the `provider` field in the signed artifact. The AI provider's response is always treated as untrusted user-generated content and is never executed or evaluated. Outbound SSRF policy differs by provider class (`services/providers/ssrf.js`):
- `openai`, `anthropic`, `gemini`, and the default `mistral` endpoint: hardcoded (or, for `mistral`, allowlist-validated) HTTPS destinations only; IP literals and private/loopback/link-local hostnames are rejected outright; `mistral`'s base URL may be overridden via `MISTRAL_BASE_URL` but is still subject to the same allowlist/HTTPS validation.
- `llama` and `local`: an intentional, narrower-trust exception. These providers are entirely operator-configured via `LLAMA_BASE_URL`/`LOCAL_BASE_URL` and the relaxed validator (`validateLocalProviderUrl`) permits `http://` and private-network/localhost destinations, since the operator is deliberately pointing QODIQA at infrastructure they control. The operator is accountable for the security of that endpoint; QODIQA enforces no allowlist or TLS requirement on it beyond requiring a parseable `http:`/`https:` URL.

See `docs/guides/providers.md` for the complete per-provider reference (capabilities, error codes, retry/timeout behavior) for the OWASP-mapped mitigation detail.

## 7. Attack Surfaces

### 7.1 HTTP Headers

| Header | Attack | Mitigation |
|--------|--------|------------|
| `X-Qodiqa-Artifact` | Forged, replayed, or expired artifact injection | 16-step `validateArtifact` + Ed25519 + expiry check + nonce registration |
| `X-Forwarded-For` | IP spoofing to bypass IP-based blocklists | `proxyValidation.js` — chain depth limit (default 10), IP format validation; `clientIpResolver.js` — forwarded headers are honoured ONLY when the immediate TCP peer matches `TRUSTED_PROXY`, otherwise ignored entirely (req.clientIp, Express `req.ip`, and the ops IP allowlist all share this trust check) |
| `X-Forwarded-Proto` | HTTP downgrade bypass | Production: `ENFORCE_HTTPS_PROTO=true` blocks non-HTTPS proto |
| `Host` | Host header injection | `QODIQA_ALLOWED_HOSTS` allowlist checked per request |
| `Content-Type` | MIME confusion / incorrect body parsing | `enforceContentType.js` middleware rejects non-JSON where JSON expected |
| `Authorization` | Leaked or brute-forced ops token | SHA-256 hashed storage; `ok_` + 256-bit random token |
| `Origin` | CORS bypass | Explicit allowlist in `corsPolicy.js`; no wildcard reflection |

### 7.2 Request Body

| Input | Attack | Mitigation |
|-------|--------|------------|
| Artifact JSON | Prototype pollution, extra fields, undefined injection | Strict schema: exactly 5 known fields; `isPlainObject` check; `hasUndefined` check |
| Payload object | Deeply nested objects, circular references | `stableStringify` canonicalization; `hasUndefined` recursive check |
| Policy JSON | Malformed policy that always permits | Structural validation in `services/policy/loader.js` (`validateAndPrepare()`) plus each evaluator's own `validate(config)`; hash-chaining detects tampering |

### 7.3 Environment Variables

| Variable | Risk | Mitigation |
|----------|------|------------|
| `QODIQA_KEY_ENCRYPTION_KEY` | Weak or placeholder KEK | `secretValidation.js` detects uniform-byte patterns, all-zeros, all-Fs at startup |
| `QODIQA_EXECUTION_INVARIANT_SECRET` | Weak/placeholder value, or identical to the KEK | `secretValidation.js` detects uniform-byte patterns and rejects a value equal to `QODIQA_KEY_ENCRYPTION_KEY` |
| `QODIQA_OPS_TOKEN` | Weak ops token | `secretValidation.js` checks against 40+ known placeholder strings; minimum length enforced |
| Signing identity API keys | N/A — always generated server-side via `crypto.randomBytes(32)`, never user-supplied, so weak/placeholder values are structurally impossible | — |
| `QODIQA_KEYS_PATH` | Repo-resident key material if left at the default path | In production, `secretValidation.js`'s `_checkProductionKeystorePath()` fails closed at startup if the resolved path lies inside the project root; this is an app-root-containment check, not `..`/NUL-byte traversal validation, and it is not enforced outside production |
| `QODIQA_AUDIT_LOG`, `POLICY_FILE` | Path traversal / misconfiguration | No path validation exists for either variable in any environment; the operator is trusted to supply a well-formed, appropriately-scoped path |
| `OPENAI_API_KEY` | Leaked to logs | Redacted in all structured log output via `logSanitizer.js` |
| `REDIS_PASSWORD`, `QODIQA_PG_PASSWORD` | Leaked to logs | `_redactUrl()` in Redis config; never included in audit events |

### 7.4 File Paths

| Path | Attack | Mitigation |
|------|--------|------------|
| `QODIQA_KEYS_PATH` (config file path, env-derived) | Repo-resident key material in production | `secretValidation.js`'s `_checkProductionKeystorePath()` — see §7.3; not enforced outside production |
| `QODIQA_AUDIT_LOG`, `POLICY_FILE` (config file paths, env-derived) | Directory/symlink traversal | None. Each is passed to `fs.readFileSync`/`fs.writeFileSync` via a plain `path.resolve()`, with no base-directory containment check and no symlink resolution; the operator is trusted to supply a well-formed, appropriately-scoped path |

### 7.5 Cryptographic Surfaces

| Surface | Attack | Mitigation |
|---------|--------|------------|
| Artifact signature | Signature reuse (V1 vulnerability) | V2 signature covers full envelope: `SHA-256("QODIQA::ARTIFACT::V1" \|\| stableStringify({expiry, payload, publicKeyId, timestamp}))` |
| Hash comparison | Timing side-channel | All hash comparisons use `crypto.timingSafeEqual()` |
| KEK wrapping | KEK compromise exposes all stored keys | KMS/HSM provider support; key rotation via `tenantKeyManager.js` |
| Domain separation | Cross-protocol signature reuse | 15 constants in `ARTIFACT_DOMAINS` (33 domain tags in all, see docs/protocol/QODIQA-PROTOCOL.md §2); one per artifact class |

## 8. Threat Assumptions

1. **The load balancer is trusted**: QODIQA assumes the proxy correctly strips client-supplied `X-Forwarded-*` headers. If the proxy does not strip these headers, an attacker can forge client IP and protocol.

2. **Redis is on a private network**: Redis does not require authentication by default. If Redis is exposed to a non-private network without authentication, nonce and anomaly stores can be tampered with.

3. **The KEK is stored securely**: The strength of the entire key management system depends on the security of `QODIQA_KEY_ENCRYPTION_KEY` (or the configured KMS). A compromised KEK allows decryption of all stored private keys.

4. **Node.js 22 TLS defaults are intact**: QODIQA does not set a custom TLS minimum version. Node.js 22 does not negotiate TLS 1.0 or 1.1 by default. This assumption is tested in the CI pipeline.

5. **The filesystem is read-only except for designated volumes**: The Docker container runs with `--read-only`. Only `/opt/qodiqa/data`, `/opt/qodiqa/logs`, `/opt/qodiqa/config`, and `/tmp` are writable.

6. **Single writer per audit log**: QODIQA's hash-chained audit log assumes a single writing process. Node.js cluster mode is detected and blocked by `processHardening.js`.

7. **Time synchronization**: Artifact timestamp validation depends on accurate system time. NTP is assumed to be configured and functioning. Maximum clock skew is bounded by `MAX_SKEW_MS` (default: per `timeCheck.js`).

## 9. Security Assumptions

1. **Ed25519 is computationally hard to forge**: No known attacks against Ed25519 with 256-bit security level.

2. **SHA-256 domain separation prevents cross-protocol attacks**: Different domain strings for each artifact class make cross-class signature reuse computationally infeasible.

3. **AES-256-GCM is semantically secure**: KEK encryption of private keys assumes AES-256-GCM with random 96-bit nonces.

4. **UUID v4 nonces provide adequate entropy**: 122-bit random requestIds make collision probability negligible for the expected request volume.

5. **npm registry integrity**: Package integrity hashes in `package-lock.json` (SHA-512 SRI) are verified by `npm ci`. The supply chain verification script adds structural checks beyond npm's built-in verification.

6. **Container isolation**: Docker `--cap-drop ALL`, `--read-only`, and `--security-opt no-new-privileges:true` are assumed to be enforced by the container runtime at deployment time. QODIQA cannot enforce these at the application layer.

## 10. Trust Relationships Summary

| From | To | Trust Type | Controls |
|------|----|------------|----------|
| Internet → Load Balancer | TLS terminated | Protocol | Operator-managed; outside QODIQA scope |
| Load Balancer → QODIQA | HTTP; partially trusted headers | Network + Header Validation | `proxyValidation.js`; `TRUSTED_PROXY` env var |
| API Consumer → QODIQA | Artifact-bearer trust | Cryptographic | Ed25519 artifact signature; 5-step pipeline |
| Operator → QODIQA | Ops-token trust | Secret + RBAC | `X-Ops-Token`; RBAC role check |
| QODIQA → Redis | Network trust | Network + Logical | Redis AUTH; TLS optional; fail-closed on error |
| QODIQA → PostgreSQL | Network + TLS trust | Network + TLS + Auth | `rejectUnauthorized: true`; `QODIQA_PG_PASSWORD` |
| QODIQA → AI Provider | HTTPS + bearer | TLS + Secret | `OPENAI_API_KEY`; HTTPS mandatory |
| CI → Supply Chain | npm registry trust | SRI Hash Pinning | `package-lock.json` SHA-512; `verify-supply-chain.js` |
